这份文档给所有模块开发对话使用。核心目标是：

```text
不要所有模块都直接在 staging 上开发。
每个模块必须在自己的 branch 或独立 worktree 里开发。
staging 只作为集成测试分支。
main 只作为正式发布分支。
```

## 分支定位

当前建议分支职责：

| 分支 | 用途 |
| --- | --- |
| `main` | 正式版本，只放准备上线或已经上线的稳定代码 |
| `staging` | 测试集成分支，多个模块确认可合并后进入这里 |
| `feature/*` | 新功能开发分支 |
| `fix/*` | 修复问题分支 |
| `chore/*` | 文档、脚本、整理类分支 |

模块开发不要直接改 `main`，也不要长期直接改 `staging`。

## 分支命名

建议格式：

```text
feature/模块名-简短目标-日期
fix/模块名-问题-日期
chore/模块名-整理-日期
```

示例：

```text
feature/user-data-import-20260529
feature/modeling-schedule-capacity-20260529
feature/product-guide-actions-20260529
feature/schedule-engine-regression-20260529
fix/project-import-preview-20260529
chore/docs-module-boundary-20260529
```

模块名建议固定：

| 模块 | 分支前缀建议 |
| --- | --- |
| 项目排期 | `schedule` |
| 排期内核 | `schedule-engine` |
| 产品组工作指引 | `product-guide` |

| 财务测算 | `finance` |
| 知识库 | `knowledge-base` |
| 送审 AI | `review-ai` |

## 每个模块开工前必须做

第一步先检查当前工作区：

```text
git status --short --branch
```

如果看到未提交修改，并且这些修改不是本轮模块自己做的：

```text
立刻停止。
不要继续开发。
不要 git reset。
不要 git checkout -- 文件。
不要随手提交别人的改动。
先把状态发给开发中控确认。
```

只有在工作区干净，或者当前分支明确就是本模块自己的分支时，才继续。

## 标准开分支流程

如果当前工作区干净：

```text
git switch staging
git pull --ff-only
git switch -c feature/模块名-目标-日期
```

然后再开始开发。

开发完成后：

```text
npm run lint
npm run build
git status --short
git add 相关文件
git commit -m "feat: xxx"
```

提交后推送自己的分支：

```text
git push -u origin feature/模块名-目标-日期
```

然后通知开发中控合并到 `staging`。

## 并行开发推荐：git worktree

如果多个对话要同时开发不同模块，最稳妥的方式不是共用同一个目录，而是用独立 worktree。

原因：

```text
同一个目录只能安全承载一个正在开发的分支。
多个对话在同一个目录里改不同模块，很容易互相覆盖、误提交或误回退。
```

建议目录：

```text
C:\Users\yuyou\Documents\Codex\2026-05-21\worktrees\
```

创建示例：

```text
git worktree add ..\worktrees\project-management-platform-user-data feature/user-data-import-20260529
git worktree add ..\worktrees\project-management-platform-modeling feature/modeling-schedule-capacity-20260529
git worktree add ..\worktrees\project-management-platform-schedule-engine feature/schedule-engine-regression-20260529
```

如果分支还不存在，可从 `staging` 创建：

```text
git worktree add -b feature/user-data-import-20260529 ..\worktrees\project-management-platform-user-data staging
```

之后对应模块对话只进入自己的 worktree 路径工作。

## 模块开发时的边界

每个 branch 只做一个模块或一个明确目标。

允许：

- 改本模块页面。
- 改本模块组件。
- 改本模块 repository / mutation / API。
- 改本模块导入导出。
- 更新本模块文档。

谨慎：

- 改 `prisma/schema.prisma`。
- 改 `src/lib/auth/`。
- 改 `src/lib/schedule-domain/`。
- 改 `src/lib/schedule-engine/`。
- 改多个模块共用的类型和工具函数。

禁止：

- 为了本模块顺手开发其他模块。
- 在本模块 branch 里批量重构无关文件。
- 把别的模块未提交改动一起提交。
- 未说明影响面就修改共享层。
- 未验证就合并到 `staging`。

## 合并到 staging 前必须确认

每个模块分支合并前，必须输出交接信息：

```text
本分支名：
本轮目标：
改动文件：
新增/修改 API：
新增/修改数据库结构：
影响的模块：
已运行验证：
未完成事项：
是否需要服务器迁移：
是否需要重启服务：
```

最低验证：

```text
npm run lint
npm run build
```

如果改了数据库：

```text
npx prisma migrate deploy
npx prisma generate
```

如果改了前端页面，需要打开对应页面验证。

## 中控合并原则

开发中控负责把模块分支合并到 `staging`。

合并顺序建议：

1. 先合并文档和纯页面改动。
2. 再合并单模块 API 改动。
3. 再合并数据库迁移。
4. 最后合并共享层改动。

如果两个分支都改了共享层，必须先由中控确认最终口径，不要让两个模块各自解释。

合并后，`staging` 必须再次运行：

```text
npm run lint
npm run build
```

必要时再部署测试服务器。

## 给模块对话的固定提示词

可以把下面这段发给每个新模块对话：

```text
请先阅读 docs/模块开发边界上下文.md 和 docs/模块分支开发规范.md。

本轮只开发当前模块。不要直接在 main 或 staging 上开发。
开工前先执行 git status --short --branch。
如果当前工作区有未提交改动，并且不是本模块自己的改动，请停止并报告，不要 reset、checkout 或提交别人的改动。

如果工作区干净，请从 staging 新建自己的模块分支：
feature/模块名-目标-日期

如果多个模块并行开发，优先使用 git worktree，为当前模块创建独立目录。

开发完成后必须运行 npm run lint 和 npm run build，并输出交接总结，等待开发中控合并到 staging。
```

## 当前特别提醒

当前项目目录曾多次出现多个模块并行修改同一工作区的情况。后续应尽量避免：

```text
一个对话在 staging 上改用户数据。
另一个对话同时在 staging 上改项目排期。
第三个对话又在 staging 上改建模排期。
```

正确做法是：

```text
用户数据一个 branch。
项目排期一个 branch。
建模排期一个 branch。
排期内核一个 branch。
最后由开发中控合并到 staging。
```
