# 产品组工作指引 - 31 个任务操作规则

最后更新：2026-05-31

适用页面：

- `/product-guide`
- 项目明细
- 工作台

关联模块：

- 项目排期
- 建模排期
- 用户与组织数据

## 1. 目标

产品组工作指引中的 31 个项目任务，必须来自项目排期的真实任务数据。

本规则用于说明：

- 哪些任务可以点击“开始”。
- 哪些任务可以点击“完成”。
- 半途接入系统的项目如何补录任务事实。
- 前置任务未完成时，普通产品组人员如何被限制。
- 管理层是否可以强制补录或强制推进。
- 产品组点击任务动作后，应该向项目排期和建模排期输出什么事件。

核心原则：

- 产品组工作指引不自己编任务。
- 产品组工作指引不自己判断延期、风险、预测完成时间。
- 产品组工作指引只提交真实执行事实。
- 项目排期负责接收事实事件，并交给排期内核重新测算。
- 建模排期负责接收款式清单、款式启动、审核和送审结果。

## 2. 任务来源

31 个任务必须从项目排期读取，不允许前端硬编码虚构任务队列。

产品组工作指引读取：

| 数据 | 用途 |
| --- | --- |
| `Project` | 项目基础信息、项目组、产品研发、产品研发美术 |
| `ProjectTask` | 每个项目下的真实任务事实字段 |
| `TaskRule` | 任务编号、任务名称、前置规则、任务模板口径 |
| `ScheduleTaskResult` | DDL、延期线、风险、预测信息、前置缺失信息 |
| `ScheduleProjectResult` | 项目整体预测、风险和当前进度 |

工作台中的任务行应至少包含：

| 字段 | 来源 |
| --- | --- |
| 项目 ID | `Project.id` |
| 项目名称 | `Project.name` |
| 项目任务 ID | `ProjectTask.id` |
| 任务编号 | `ProjectTask.taskNo` 或任务规则 |
| 任务名称 | `ProjectTask.taskName` 或任务规则 |
| 当前状态 | `ProjectTask.status` |
| 实际开始日期 | `ProjectTask.actualStartDate` |
| 实际完成日期 | `ProjectTask.actualFinishDate` |
| 计划 / 预测 / DDL | `ScheduleTaskResult` |
| 延期线 | `ScheduleTaskResult` |
| 前置缺失 | `ScheduleTaskResult.missingActualPredecessorIds` 或任务规则计算结果 |

## 3. 页面分工

### 3.1 项目明细

项目明细必须列出该项目的全部 31 个真实任务。

项目明细中的任务行用于查看任务状态，并进入对应工作台。

项目明细不直接承担复杂任务处理。

### 3.2 工作台

工作台是操作单个任务的地方。

每个任务点击后进入该任务自己的工作台界面。

不同任务可以有不同的操作内容，例如：

- 市场调研类任务：开始、完成、备注。
- 原画类任务：上传图、确认过审、触发款式清单。
- 建模相关任务：通知建模排期启动第一款或其余款。
- 审核类任务：进入审批中心，不进入普通任务处理。
- 送审类任务：提交送审结果、附件和反馈。

工作台不应使用统一的虚构任务模板替代真实任务操作。

### 3.3 任务队列

工作台任务队列只展示未完成任务。

已完成任务仍可在项目明细中查看，但不应混入每日处理队列。

## 4. 角色与权限

### 4.1 普通产品组人员

普通产品组人员包括：

- 产品研发
- 产品研发美术

普通产品组人员可以：

- 在前置条件满足时点击“开始”。
- 在前置条件满足时点击“完成”。
- 对半途接入项目补录完成时间。
- 提交款式清单、任务 7 / 10 建模启动事件、产品审核 / 送审结果。
- 查看前置缺失原因。
- 查看事件提交结果。

普通产品组人员不可以：

- 忽略前置任务强制开始。
- 忽略前置任务强制完成。
- 修改排期预测、风险、延期结论。
- 直接修改建模状态、建模师、外包供应商或建模进度。

### 4.2 管理层后门

需要保留管理层后门。

原因：

- 很多项目是半途接入系统，历史任务可能已经线下完成。
- 项目任务数据可能晚于真实执行录入。
- 项目排期的前置任务可能暂时缺事实字段，但业务上已经允许继续推进。
- 管理层需要一次性补齐历史事实，避免产品组被系统卡死。

管理层后门适用角色：

- 产品总监
- 管理员
- 被明确授权的项目管理角色

管理层后门能力：

- 强制开始任务。
- 强制完成任务。
- 在缺少前置完成记录时补录事实。

管理层强制操作必须填写原因。

强制原因会进入事件 payload，供项目排期记录、追溯和排查。

第一版权限口径：

- 普通 `task_started` / `task_completed` 允许产品组账号写入。
- 带 `override = true` 的强制开始 / 强制完成只允许 `admin / manager`。
- 产品组提交给建模排期的款式清单、任务 7 / 10 启动事件、审核 / 送审结果允许产品组账号写入。

## 5. 普通“开始”按钮规则

说明：

- `ProjectTask.id` 是已存在任务事实记录的 ID。
- 对于半途接入项目，如果某个任务还没有 `ProjectTask.id`，产品组仍可用 `projectId + taskNo` 向项目排期提交事实事件。
- 项目排期收到事件后，负责按任务规则初始化缺失的 `ProjectTask`。
- 因此开始 / 完成按钮的最低身份条件是系统项目 ID 和任务编号；`projectTaskId` 是推荐字段，不是普通任务事实事件的硬性前置。

### 5.1 可以点击开始

满足以下条件时，普通产品组人员可以点击“开始”：

- 任务存在真实 `projectId`。
- 任务存在有效 `taskNo`。
- 任务未完成。
- 任务没有实际开始日期。
- 任务没有处于进行中、送审中、阻塞、暂停等已启动状态。
- 任务没有缺失的前置任务。

点击“开始”后，产品组工作指引向项目排期发送 `task_started` 事件。

普通开始时如果用户没有手动选择实际开始日期，页面可以默认使用当天日期。

### 5.2 不可以点击开始

以下情况普通开始按钮应禁用：

| 情况 | 页面提示 |
| --- | --- |
| 任务已完成 | 该任务已完成，无需再次开始 |
| 任务已开始 | 该任务已经开始 |
| 任务缺少项目 ID 或任务编号 | 任务数据不完整，无法提交 |
| 前置任务未完成 | 请先完成前置任务 |
| 任务已暂停 | 当前任务已暂停，请先恢复后再处理 |
| 任务已取消 | 当前任务已取消，不能开始 |

如果前置任务未完成，页面必须显示缺失的前置任务名称或编号。

示例：

```text
当前任务暂不能开始，因为前置任务 #3 方案确认 尚未完成。
```

## 6. 普通“完成”按钮规则

### 6.1 可以点击完成

满足以下条件时，普通产品组人员可以点击“完成”：

- 任务存在真实 `projectId`。
- 任务存在有效 `taskNo`。
- 任务未完成。
- 任务没有缺失的前置任务。

允许任务未点击“开始”就直接补录完成。

这是为了支持半途接入系统的项目。

补录完成时：

- 必须填写实际完成日期。
- 可以填写实际开始日期。
- 可以填写备注。
- 如果填写了实际开始日期，项目排期仅在原任务没有实际开始日期时补写。
- 如果不填写实际开始日期，不应由产品组工作指引强行编造。

### 6.2 不可以点击完成

以下情况普通完成按钮应禁用：

| 情况 | 页面提示 |
| --- | --- |
| 任务已完成 | 该任务已完成，无需再次完成 |
| 任务缺少项目 ID 或任务编号 | 任务数据不完整，无法提交 |
| 前置任务未完成 | 请先完成前置任务，或由管理层补录 |
| 任务已取消 | 当前任务已取消，不能完成 |

如果前置任务未完成，普通产品组人员不能直接完成。

页面应提供清晰说明，并显示管理层补录入口。

示例：

```text
当前任务暂不能完成，因为前置任务 #7 精细建模确认风格 尚未记录完成。
如该前置任务已在线下完成，请由管理层补录。
```

## 7. 管理层强制开始 / 完成规则

### 7.1 强制开始

管理层可以在前置任务缺失时强制开始当前任务。

强制开始必须填写：

- 实际开始日期。
- 强制原因。

强制开始仍然发送 `task_started` 事件。

事件 payload 必须额外包含：

```json
{
  "override": true,
  "overrideType": "force_start",
  "overrideReason": "历史项目已在线下开始，现补录系统事实",
  "missingPredecessorIds": ["task-id-1", "task-id-2"]
}
```

### 7.2 强制完成

管理层可以在前置任务缺失时强制完成当前任务。

强制完成必须填写：

- 实际完成日期。
- 强制原因。

可以填写：

- 实际开始日期。
- 备注。

强制完成仍然发送 `task_completed` 事件。

事件 payload 必须额外包含：

```json
{
  "override": true,
  "overrideType": "force_complete",
  "overrideReason": "历史项目已在线下完成，现补录系统事实",
  "missingPredecessorIds": ["task-id-1", "task-id-2"]
}
```

### 7.3 管理层强制不等于修改排期结论

管理层强制操作只代表录入任务事实。

产品组工作指引不因此写入：

- 风险等级
- 是否延期
- 预测完成时间
- 预测上线时间
- 里程碑状态

这些仍由项目排期内核重新测算。

## 8. 项目排期事件输出

产品组工作指引第一版只向项目排期发送两类事件：

```text
task_started
task_completed
```

统一接口：

```text
POST /api/schedule/task-fact-events
```

### 8.1 task_started

触发场景：

- 普通开始。
- 管理层强制开始。

最小事件：

```json
{
  "eventId": "product-guide:task-event:uuid",
  "eventType": "task_started",
  "sourceModule": "product-guide",
  "projectId": "系统项目 ID",
  "taskNo": 1,
  "taskKey": "#1",
  "taskName": "市场调研",
  "occurredAt": "2026-05-31T10:30:00+08:00",
  "operatorId": "当前用户 ID",
  "operatorName": "当前用户名称",
  "payload": {
    "actualStartDate": "2026-05-31",
    "status": "进行中",
    "note": "已开始推进"
  }
}
```

日期字段使用 `YYYY-MM-DD`。

`occurredAt` 使用带时区 ISO 字符串。

### 8.2 task_completed

触发场景：

- 普通完成。
- 半途接入项目补录完成。
- 管理层强制完成。

最小事件：

```json
{
  "eventId": "product-guide:task-event:uuid",
  "eventType": "task_completed",
  "sourceModule": "product-guide",
  "projectId": "系统项目 ID",
  "taskNo": 1,
  "taskKey": "#1",
  "taskName": "市场调研",
  "occurredAt": "2026-05-31T10:30:00+08:00",
  "operatorId": "当前用户 ID",
  "operatorName": "当前用户名称",
  "payload": {
    "actualFinishDate": "2026-05-31",
    "status": "已完成",
    "note": "已确认完成"
  }
}
```

如果用户填写了实际开始日期，可以补充：

```json
{
  "actualStartDate": "2026-05-28"
}
```

项目排期侧规则：

- 如果原任务已有实际开始日期，不覆盖。
- 如果原任务没有实际开始日期，可以补写。

## 9. 建模排期特殊联动

### 9.1 款式清单提交

原画里程碑完成时，产品组需要提交完整建模款式清单给建模排期。

提交接口：

```text
POST /api/modeling/style-submissions
```

规则：

- 提交完整系列款式清单。
- 必须且只能有 1 个 `isFirstModelingStyle = true`。
- 第一款挂任务 7。
- 其余款挂任务 10。
- 提交款式清单不代表建模开始。
- 建模排期确认后，款式状态先进入未启动或相应确认状态。

如果当前任务是原画里程碑收口任务，并且项目还没有提交完整款式清单，完成任务前应先弹出建模款式清单界面。

### 9.2 任务 7 启动

任务 7 点击开始并且项目排期 `task_started` 事件成功后，产品组工作指引额外通知建模排期启动第一款。

接口：

```text
POST /api/modeling/style-start-events
```

payload 关键字段：

```json
{
  "projectId": "系统项目 ID",
  "projectTaskId": "任务 7 的 ProjectTask ID",
  "taskNo": 7,
  "startScope": "first-style"
}
```

如果任务 7 在页面读取时还没有 `projectTaskId`，产品组工作指引应先发送项目排期 `task_started` 事件，并使用项目排期返回的 `projectTaskId` 补充到建模启动事件中。

建模排期处理：

```text
第一款：未启动 -> 未分配
```

### 9.3 任务 10 启动

任务 10 点击开始并且项目排期 `task_started` 事件成功后，产品组工作指引额外通知建模排期启动其余款式。

接口：

```text
POST /api/modeling/style-start-events
```

payload 关键字段：

```json
{
  "projectId": "系统项目 ID",
  "projectTaskId": "任务 10 的 ProjectTask ID",
  "taskNo": 10,
  "startScope": "remaining-styles"
}
```

如果任务 10 在页面读取时还没有 `projectTaskId`，产品组工作指引应先发送项目排期 `task_started` 事件，并使用项目排期返回的 `projectTaskId` 补充到建模启动事件中。

建模排期处理：

```text
其余款式：未启动 -> 未分配
```

### 9.4 任务 8 / 9

任务 8 和任务 9 不触发款式级建模任务启动。

它们只向项目排期发送普通任务事实事件。

## 10. 按钮状态

每个任务在工作台中至少有以下状态：

| 状态 | 普通开始 | 普通完成 | 管理层入口 | 说明 |
| --- | --- | --- | --- | --- |
| 未开始，前置满足 | 可点 | 可补录完成 | 可见但不优先 | 正常处理 |
| 未开始，前置缺失 | 禁用 | 禁用 | 可强制 | 显示缺失前置 |
| 进行中 | 不显示或禁用 | 可点 | 可见但不优先 | 正常完成 |
| 送审中 | 不显示或禁用 | 按任务类型判断 | 可见但不优先 | 审核类任务进入审批中心 |
| 阻塞 | 不显示或禁用 | 禁用 | 可强制 | 需要先解除或管理层处理 |
| 暂停 | 不显示或禁用 | 禁用 | 可强制 | 暂停不是阻塞 |
| 已完成 | 不显示或禁用 | 不显示或禁用 | 不显示 | 只展示完成事实 |
| 已取消 | 禁用 | 禁用 | 不建议显示 | 取消任务不通过完成处理 |

按钮文案建议：

| 场景 | 文案 |
| --- | --- |
| 正常开始 | 开始 |
| 正常完成 | 完成 |
| 未开始但补录完成 | 补录完成 |
| 前置缺失 | 前置未完成 |
| 管理层强制开始 | 管理层强制开始 |
| 管理层强制完成 | 管理层强制完成 |
| 已完成 | 已完成 |

## 11. 工作台判定流程

### 11.1 开始按钮判定

```text
1. 如果任务缺少 projectId / taskNo，禁用。
2. 如果任务已完成，禁用。
3. 如果任务已有 actualStartDate，显示已开始。
4. 如果任务状态属于进行中 / 送审中 / 阻塞 / 暂停，显示已开始或当前状态。
5. 如果存在 missingActualPredecessorIds，普通开始禁用，并显示前置缺失。
6. 否则允许普通开始。
7. 如果当前用户是管理层，且前置缺失，显示强制开始入口。
```

### 11.2 完成按钮判定

```text
1. 如果任务缺少 projectId / taskNo，禁用。
2. 如果任务已完成，禁用。
3. 如果任务已取消，禁用。
4. 如果存在 missingActualPredecessorIds，普通完成禁用，并显示前置缺失。
5. 否则允许普通完成或补录完成。
6. 如果当前用户是管理层，且前置缺失，显示强制完成入口。
```

### 11.3 事件发送顺序

普通任务：

```text
用户点击开始 / 完成
-> 产品组工作指引校验按钮规则
-> POST /api/schedule/task-fact-events
-> 显示项目排期接收结果
```

任务 7 / 10 开始：

```text
用户点击开始
-> 产品组工作指引校验按钮规则
-> POST /api/schedule/task-fact-events
-> 项目排期成功接收
-> POST /api/modeling/style-start-events
-> 分开展示项目排期结果和建模排期结果
```

如果项目排期事件失败，不应继续发送建模启动事件。

如果建模启动事件失败，不应回滚项目排期事件，只需要在页面展示建模通知失败原因，供用户重试或排查。

## 12. 审批中心与消息提醒

建模排期主动回传给产品组的事件，不应混进普通任务队列。

产品组工作台需要有消息提醒子页面，用于承载外部模块回传通知。

当前建模排期会回传：

| 事件 | 产品组处理位置 |
| --- | --- |
| `style_list_confirmed` | 消息提醒 |
| `style_list_returned` | 消息提醒 |
| `modeling_work_submitted` | 审批中心 |

其中 `modeling_work_submitted` 不应该点击后进入普通任务处理。

它应进入审批中心，由产品研发美术进行内部审核或送审处理。

## 13. 失败处理

### 13.1 项目排期事件失败

如果 `POST /api/schedule/task-fact-events` 失败，页面必须展示：

- 当前动作名称。
- 接口状态码。
- 项目排期返回的 `message`。
- 发送的事件内容。

示例：

```text
任务开始 -> 项目排期未成功。
原因：找不到对应任务规则，无法初始化 ProjectTask。
```

### 13.2 建模启动事件失败

如果任务 7 / 10 的建模启动事件失败，页面必须展示：

- 项目排期事件是否成功。
- 建模排期接口状态码。
- 建模排期返回的 `message`。
- 命中的款式数量、启动数量、跳过数量。

项目排期事件成功但建模事件失败时，不能把任务状态改回未开始。

## 14. 验收标准

### 14.1 普通任务

- 未完成任务出现在工作台任务队列。
- 已完成任务不出现在工作台任务队列。
- 项目明细仍能看到全部 31 个真实任务。
- 点击未完成任务可以进入对应工作台。
- 前置任务满足时，可以点击开始。
- 点击开始后，成功发送 `task_started`。
- 前置任务满足时，可以点击完成。
- 点击完成后，成功发送 `task_completed`。

### 14.2 半途接入项目

- 未点击开始的任务可以补录完成。
- 补录完成必须填写实际完成日期。
- 可以选择填写实际开始日期。
- 补录完成仍发送 `task_completed`。

### 14.3 前置缺失

- 前置任务未完成时，普通开始按钮禁用。
- 前置任务未完成时，普通完成按钮禁用。
- 页面显示缺失的前置任务。
- 普通产品组人员不能绕过前置限制。

### 14.4 管理层后门

- 管理层可以看到强制开始 / 强制完成入口。
- 强制操作必须填写原因。
- 强制操作发送标准 `task_started` / `task_completed`。
- 事件 payload 包含 `override = true`。
- 事件 payload 包含 `overrideReason`。
- 事件 payload 包含缺失前置任务信息。

### 14.5 建模联动

- 任务 7 开始成功后，通知建模排期启动第一款。
- 任务 10 开始成功后，通知建模排期启动其余款式。
- 任务 8 / 9 不通知建模排期启动款式。
- 项目排期事件失败时，不发送建模启动事件。
- 建模启动失败时，页面能单独展示失败原因。

## 15. 不在本规则内的事项

以下事项不在本规则内实现：

- 登录权限完整系统。
- 项目排期内核重算逻辑。
- 建模排期内部状态机。
- 建模师分配。
- 外包供应商分配。
- 风险等级计算。
- 预测上线日期计算。
- 任务模板大范围重构。

本规则只定义产品组工作指引中 31 个任务的“开始 / 完成 / 补录 / 强制处理”行为，以及这些行为应该输出的跨模块事件。
