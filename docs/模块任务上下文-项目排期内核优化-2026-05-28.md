## 一句话目标

平台必须只有一个排期真相来源：

```text
不经过排期内核，就拿不到合法排期结果。
不写入执行事实，就不能影响预测。
不重新测算，就不能声称预测已经更新。
```

项目排期、产品组工作指引、建模排期、上线日历、未来财务测算，都只能读取统一排期结果，不应该各自重新解释任务编号、里程碑、预测完成时间、风险等级。

## 最核心文件

### 旧脚本内核

```text
legacy/schedule-engine/project-schedule-core.cjs
legacy/schedule-engine/project-analysis-v5-excel.cjs
legacy/schedule-engine/extract_project_excel.py
legacy/schedule-engine/generate-weekly-analysis.cjs
```

职责：

- `project-schedule-core.cjs`：排期日期计算核心，例如加减工作日、任务间隔、排期天数。
- `project-analysis-v5-excel.cjs`：当前最重要的项目排期分析脚本，接收结构化项目、实际进度、任务规则，输出项目级和任务级预测结果。
- `extract_project_excel.py`：从历史 Excel 中提取项目信息、实际进度、任务规则。注意它适合完整项目排期源表，不适合“项目主数据导入表”。
- `generate-weekly-analysis.cjs`：周度/月度任务分析相关脚本，后续应逐步改为读取统一内核结果。

## 当前输入口径

### 项目输入

最少必填：

```text
项目名称
版权方
IP
```

系统应生成永久项目 ID。项目编号如 `26015` 可能后补、可能改，不应作为唯一身份。

项目名称很少改，但允许改。项目拆分、取消后复活都算新项目；延期到下一年仍是同一个项目。

### 规划输入

项目排期的规划视图只能接受管理层或产品总监层面的规划输入。

规划字段可以通过项目主数据 Excel 合并补充。前期允许 Excel 覆盖网页数据。未来可分为：

- 合并补充：常规操作。
- 全量替换：高风险操作，只允许管理员。

### 执行事实输入

压力预测和预测视图应接受：

- 产品组工作指引写入的任务完成、预计完成、阻塞、进度备注、送审节点。
- 建模排期写入的款式建模状态、内部通过、版权方过审、驳回修改、外包事实。
- 旧 Excel 或脚本导入的实际进度。

预测日期、风险等级、产能超载等计算结果不能手填。

## 当前输出口径

### 项目级输出

`ScheduleProjectResult` 应表达：

- 原计划上线日期。
- 预测上线日期。
- 延期天数。
- 风险等级。
- 当前阶段。
- 当前关键任务。
- 项目进度百分比。
- 风险提示文案。

### 任务级输出

`ScheduleTaskResult` 应表达：

- 任务编号。
- 任务名称。
- 里程碑类型。
- 计划开始/完成。
- 预测开始/完成。
- 预计完成。
- 实际完成。
- 展示状态。
- 延期/风险信息。
- 原始脚本结果。

### 任务卡输出

`TaskCard` 是看板拖拽的视觉卡片。当前项目排期页中，项目卡只显示项目名称，点进详情再看完整信息。

## 当前重要业务规则

### 里程碑映射

当前口径：

| 里程碑 | 任务编号 |
| --- | --- |
| 原画里程碑 | 1-6 |
| 建模里程碑 | 7-10 |
| 红蜡里程碑 | 11-15、17、18 |
| 产前里程碑 | 21-27 |
| 大货里程碑 | 30 |
| 平面里程碑 | 其他平面设计任务编号 |

注意：平面里程碑不是“兜底垃圾桶”。这些任务本身就是平面设计需要完成的任务，只是任务编号跨度较大。

未来任务编号和模板可能变化，应逐步从硬编码升级为配置表。

### 规划视图和预测视图

规划视图：

```text
优先 plannedFinishDate
其次 expectedFinishDate
最后 forecastFinishDate
```

预测视图：

```text
如果任务已完成：actualFinishDate -> forecastFinishDate -> expectedFinishDate -> plannedFinishDate
如果任务未完成：forecastFinishDate -> expectedFinishDate -> plannedFinishDate
```

一个里程碑如果已经全部完成，应固定在实际完成月份，而不是计划月份。

如果实际完成晚于计划完成，应显示为“延期完成”。视觉上可以用深绿色区别于正常完成。

### 上线日历

年度规划单位是春节后的第一个月到下一个春节，共 12 个月。

上线日历显示当月应上线项目，并支持切换年度。

月度上线数量：

- 硬规则：不少于 2 个，不超过 5 个。
- 软目标：3-4 个。

### 手动调整规划

管理层手动调整规划里程碑时，允许单独调整某个里程碑月份，但只允许向前调整，不允许向后调整。

上线日历中拖动项目，本质是调整项目规划上线月份。调整保存后必须重新测算，才能更新预测视图和风险。

### 建模相关口径

建模里程碑对应任务 7-10。

原画过审后产生 7-14 款原画设计稿，每个原画设计稿对应一款建模。建模必须在原画过审后开始，特殊提前情况需要审批备注。

所有款式都完成且版权方送审通过，项目级“根据效果图建模”才算完成。部分款式完成不能推进后续任务。

建模排期写入款式事实后，只提供任务 7 / 10 必做款式是否全部通过、最后通过日期、未通过款式和阻塞款式等可读事实。是否写项目任务执行事实、是否重新测算，由项目排期模块主动读取后自行决定。

## 回归样本

每次改排期脚本、导入、展示、日期选择、里程碑聚合，都必须检查：

| 项目 | 检查点 |
| --- | --- |
| 小鸟4代 | 延期完成口径。已完成项目如果实际完成晚于规划完成，应显示延期完成，不应继续显示当前风险。 |
| 兔老大表情包mini | 前置任务填表错误识别。预测异常时优先检查实际进度填表，不要用代码绕过错误数据。 |
| 无牙仔猫猫 | 启动晚导致整体预测晚。有效启动显著晚于理论启动时，整体预测后移是合理结果。 |
| 插画小人mini2代 | 任务 10 已开始但任务 7 未完成异常。应提示前置事实缺失，而不是直接改脚本跳过。 |

这些样本已写入：

但目前还没有完整自动化回归测试。优化内核时建议补一组最小测试脚本或调试命令，输出这些项目的关键字段。

## 最近一次重要事故和修复

2026-05-28 前后出现过一次导入边界问题：

用户上传的是“项目主数据导入表”，不是完整排期源表。旧的项目排期 Excel 直接导入入口把它当成排期源表处理，脚本得到 0 个项目，并可能清空排期相关数据。

已做修复：

- `src/app/api/schedule/import-excel/route.ts`：旧的排期 Excel 直接导入入口已禁用，返回 410，提示使用“数据导入预览”。
- `src/lib/schedule-import/actual-schedule-import.ts`：导入旧脚本 JSON 结果前增加保护，如果项目数或任务数为 0，拒绝写库，避免清空数据。
- 服务器已用真实排期 JSON 恢复过一次数据，恢复后大致为 44 个项目、1324 条项目任务、674 条未来任务卡。

新对话优化内核时，不要重新打开无预览、无保护的 Excel 直写入口。

## 推荐优化顺序

1. 先读旧脚本：`project-analysis-v5-excel.cjs` 和 `project-schedule-core.cjs`。
2. 明确脚本输入输出结构，给关键字段写中文注释或独立说明。
3. 把任务编号、任务模板、里程碑映射从硬编码逐步迁移到配置表或统一领域层。
4. 给回归样本补一个可运行检查工具，至少输出四个样本项目的计划、实际、预测、风险和异常原因。
5. 改 `schedule-engine/adapters.ts`，确保数据库输入到旧脚本的转换没有丢字段。
6. 改 `persistScheduleAnalysis`，确保脚本结果写入 `ScheduleProjectResult`、`ScheduleTaskResult`、`TaskCard`、`Alert` 的口径统一。
7. 最后再调整 `schedule-repository.ts` 和页面展示。

每一步都要运行：

```text
npm run lint
npm run build
```

如果改了数据库结构，还要补 Prisma migration，并在部署前执行：

```text
npx prisma migrate deploy
npx prisma generate
```
