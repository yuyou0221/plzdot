# P0 数据库迁移分阶段方案

最后更新：2026-05-27

本文档把《P0 数据字典》和《现有 Prisma Schema 对照改造清单》转成工程执行计划。目标是分阶段改造数据库和导入接口，而不是一次性重写全部 schema。

当前已有迁移：

```text
prisma/migrations/20260522015000_init_p0
prisma/migrations/20260525033000_add_user_auth_fields
```

## 总原则

- 每个阶段都要能独立上线、独立回滚。
- 每个阶段迁移前必须备份数据库。
- 不在同一阶段同时大改项目排期、产品组工作指引、建模排期和用户数据。
- 旧字段先保留兼容，不急着删除。
- 页面读取新字段时必须有旧字段回退。
- Excel 导入先支持新旧字段并行，等数据稳定后再清理旧字段。
- 排期预测、风险等级、超载判断仍只能由系统计算，不允许 Excel 或页面手填。

## 阶段总览

| 阶段 | 目标 | 风险 | 是否建议先做 |
| --- | --- | --- | --- |
| 0 | 迁移前准备、备份、数据快照 | 低 | 是 |
| 1 | 补项目主数据结构 | 中 | 是 |
| 2 | 补款式与建模结构 | 高 | 是，但要在阶段 1 稳定后 |
| 3 | 补产品组工作指引事实结构 | 中 | 是 |
| 4 | 组织、岗位、产能细化 | 中 | 是 |
| 5 | 清理旧字段和技术债 | 高 | 暂缓 |

建议顺序：

```text
阶段 0 -> 阶段 1 -> 阶段 4 -> 阶段 2 -> 阶段 3 -> 阶段 5
```

理由：

- 阶段 1 解决项目、版权方、IP、产品类型这些全站基础。
- 阶段 4 让用户数据先支撑项目组、建模师、产能。
- 阶段 2 再处理款式和建模，避免缺人员和产能基础。
- 阶段 3 最后让产品组工作指引正式成为执行事实入口。

## 阶段 0：迁移前准备

目标：建立可恢复、可对比、可验收的改库流程。

### 数据库动作

不改 schema。

必须准备：

- 本地数据库备份命令。
- staging 数据库备份命令。
- 备份文件保存路径。
- 迁移前数据统计脚本。
- 迁移后数据统计脚本。

建议统计项：

| 数据 | 统计 |
| --- | --- |
| 项目 | `Project` 数量 |
| 项目任务 | `ProjectTask` 数量 |
| 排期结果 | 最新 `ScheduleRun`、`ScheduleProjectResult`、`ScheduleTaskResult` 数量 |
| 建模任务 | `ModelingTask` 数量 |
| 建模反馈 | `ModelingFeedback` 数量 |
| 用户 | `User` 数量 |
| 团队 | `Team` 数量 |
| 外包 | `OutsourceVendor` 数量 |

### 代码动作

- 新增迁移检查脚本或临时检查命令。
- 文档记录备份路径和恢复方式。
- 不改页面。

### 验收

- 本地可备份数据库。
- staging 可备份数据库。
- 能输出迁移前关键表数量。
- 能确认当前四个页面能打开：
  - `/`
  - `/product-guide`
  - `/modeling`
  - `/users`

### 回滚

阶段 0 不改 schema，无需回滚。

## 阶段 1：补项目主数据结构

目标：让项目不再依赖纯字符串字段表达版权方、IP、产品类型和年度规划。

### Prisma 新增模型

新增：

- `Licensor`
- `IpAsset`
- `ProjectIp`
- `ProductType`
- `PlanningCycle`

### Prisma 修改模型

修改 `Project`，新增字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `businessProjectCode` | `String?` | 长期业务编号字段，兼容 `projectCode` |
| `primaryLicensorId` | `String?` | 主版权方 |
| `productTypeId` | `String?` | 产品类型 |
| `seriesGeneration` | `String?` | 系列代数 |
| `targetYear` | `Int?` | 目标年份 |
| `urgencyLevel` | `String?` | 紧急程度 |
| `planningCycleId` | `String?` | 春节年度周期 |
| `plannedLaunchMonth` | `String?` | 计划上线月份，例如 `2026-12` |
| `suggestedLaunchDate` | `DateTime? @db.Date` | 系统建议上线日期 |
| `expectedStyleCount` | `Int?` | 预估款式数，兼容 `styleCount` |

短期保留旧字段：

- `projectCode`
- `projectName`
- `ipName`
- `licensorName`
- `productType`
- `styleCount`
- `plannedLaunchDate`

### 数据迁移动作

从现有 `Project` 扫描并生成：

- `Licensor`：来自 `Project.licensorName`
- `IpAsset`：来自 `Project.ipName`
- `ProductType`：来自 `Project.productType`
- `ProjectIp`：绑定项目和 IP
- `Project.primaryLicensorId`
- `Project.productTypeId`
- `Project.businessProjectCode = Project.projectCode`
- `Project.expectedStyleCount = Project.styleCount`
- `Project.plannedLaunchMonth = plannedLaunchDate` 的年月

注意：

- 如果 `licensorName` 为空，不能生成假版权方。
- 如果 `ipName` 为空，保留空值并加入数据质量报告。
- 如果同名 IP 出现在不同版权方下，应按版权方拆分。

### 导入脚本动作

项目排期 Excel 导入需要支持：

- 继续读取旧格式。
- 导入时自动 upsert `Licensor`、`IpAsset`、`ProductType`。
- 写入 `ProjectIp`。
- 写入新字段，同时保留旧字段。

### 页面动作

项目排期页面：

- 展示时优先读取结构化字段。
- 结构化字段为空时回退旧字符串字段。

上线日历：

- 优先使用 `plannedLaunchMonth`。
- `suggestedLaunchDate` 由系统计算，不让用户直接编辑。

用户数据、建模排期、产品组工作指引：

- 暂不强制修改，只保证原页面不坏。

### 验收

数据验收：

- 项目数量不变。
- 每个非空 `licensorName` 都生成或匹配一个 `Licensor`。
- 每个非空 `ipName` 都生成或匹配一个 `IpAsset`。
- 每个项目的 `plannedLaunchMonth` 与原 `plannedLaunchDate` 年月一致。
- 原项目排期导入仍能跑通。

页面验收：

- `/` 项目排期正常加载。
- 规划视图、预测视图、上线日历正常。
- 已知项目如小鸟4代仍能显示。
- Excel 导入后项目数量合理。

回归样本：

- 小鸟4代
- 兔老大表情包mini
- 无牙仔猫猫
- 插画小人mini2代

### 回滚

低风险回滚方式：

- 不删除旧字段，所以页面可回退到旧字段读取。
- 如果迁移失败，恢复迁移前数据库备份。
- 如果代码有问题，回滚 Git 到迁移前版本，但数据库新增表保留不影响旧代码。

## 阶段 4：组织、岗位、产能细化

建议把阶段 4 提前到阶段 2 前执行，因为建模产能依赖用户数据。

目标：让用户数据能稳定支撑项目组、岗位、建模师产能。

### Prisma 新增模型

新增：

- `UserBusinessRole`
- `ModelerCapacity`

### Prisma 修改模型

修改 `User`，新增字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `departmentId` | `String?` | 公司部门 |
| `primaryProjectTeamId` | `String?` | 主要项目小组 |
| `defaultWeeklyWorkdays` | `Float?` | 默认每周可用工作日 |

继续保留：

- `teamId`
- `roleTitle`
- `weeklyCapacityStyles`

但 `weeklyCapacityStyles` 不再参与新产能计算。

### Team 口径

P0 不拆 `Department` 和 `ProjectTeam` 两张表，先复用 `Team`。

建议约定：

| `teamType` | 说明 |
| --- | --- |
| `department` | 公司部门 |
| `projectTeam` | 产品项目小组 |

项目小组通过 `parentTeamId` 指向产品团队。

### 数据迁移动作

- 把产品团队、原画团队、建模团队等写为 `teamType = department`。
- 把忍者组、迪no组、丹东组、易特凡组写为 `teamType = projectTeam`。
- 将项目小组的 `parentTeamId` 指向产品团队。
- 根据现有 `User.teamId` 尝试写入 `departmentId` 或 `primaryProjectTeamId`。
- 根据 `User.roleTitle` 生成 `UserBusinessRole`。
- 根据现有建模师，写入 `defaultWeeklyWorkdays`，未知时允许为空并在页面提示。

### 导入脚本动作

用户组织 Excel 导入需要支持：

- 公司部门。
- 项目小组。
- 一人多业务角色。
- 默认每周可用工作日。
- 建模师标记。

### 页面动作

用户数据页：

- 区分人员信息、账号权限、组织归属、业务角色、建模产能。
- 建模能力标签暂时隐藏或降级。
- 建模师产能使用工作日口径。

建模排期：

- 读取 `defaultWeeklyWorkdays` 和 `ModelerCapacity`。
- 若缺产能，显示待补充。

产品组工作指引：

- 后续可用当前登录用户匹配项目小组。

### 验收

- 用户数量不变。
- 公司部门和项目小组能区分。
- 一个人可以有多个业务角色。
- 建模师列表仍能在建模排期读取。
- 建模超载不再使用款式数，改用工作日。

### 回滚

- 旧页面仍可用 `teamId` 和 `roleTitle`。
- 如果新组织结构错误，恢复数据库备份或重新导入用户组织 Excel。

## 阶段 2：补款式与建模结构

目标：把款式从建模任务里抽出来，支持产品组工作指引维护真实款式清单。

### Prisma 新增模型

新增：

- `Style`
- `ModelingAssignmentHistory`

如果阶段 4 已完成，则 `ModelerCapacity` 已存在，不在本阶段重复做。

### Prisma 修改模型

修改 `ModelingTask`，新增字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `styleId` | `String?` | 关联款式，迁移期可为空 |
| `internalApprovedAt` | `DateTime? @db.Date` | 建模内部通过日期 |
| `submittedAt` | `DateTime? @db.Date` | 最近送审日期 |
| `approvedAt` | `DateTime? @db.Date` | 版权方过审日期 |

修改 `ModelingFeedback`，新增字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `submittedAt` | `DateTime?` | 本轮送审时间 |

现有 `feedbackAt` 继续表示收到反馈时间。

### 数据迁移动作

从现有 `ModelingTask` 生成 `Style`：

| `ModelingTask` 字段 | `Style` 字段 |
| --- | --- |
| `projectId` | `projectId` |
| `styleCode` | 尝试解析为 `styleSequence`，失败则按项目内顺序生成 |
| `styleName` | `name` |
| `estimatedWorkdays` | `estimatedModelingWorkdays` |
| `originalArtApprovedDate` | `artworkApprovedAt` |
| `isRequired` | `isRequired` |

然后回写：

- `ModelingTask.styleId`
- `Style.modelingStartedAt = ModelingTask.actualStartDate`
- `Style.modelingApprovedAt = ModelingTask.actualFinishDate`，仅当状态为已通过时可写

注意：

- 只迁移真实 `ModelingTask`。
- 虚拟款式不能写入 `Style`。
- 如果 `styleCode` 重复，要生成数据质量报告。

### 导入脚本动作

建模 Excel 导入需要支持：

- 优先匹配 `Style`。
- 没有 `Style` 时创建 `Style` 和 `ModelingTask`。
- 状态变化要记录。
- 换建模师要写 `ModelingAssignmentHistory`。

产品组工作指引：

- 新增款式时写 `Style`。
- 如果款式需要建模，同时生成或关联 `ModelingTask`。

### 页面动作

建模排期：

- 款式名称优先从 `Style` 读取。
- 建模状态继续从 `ModelingTask` 读取。
- 显示内部通过、送审、版权方通过字段。
- 换人时弹窗记录当前进度和原因。

产品组工作指引：

- 款式清单页写入 `Style`。
- 原画过审日期写入 `Style.artworkApprovedAt`。
- 原画未过审提前建模时要求审批备注。

### 验收

数据验收：

- 迁移后 `Style` 数量应等于真实建模款式数，或大于等于产品组已录入款式数。
- 每条真实 `ModelingTask` 应有 `styleId`。
- 建模排期不显示虚拟数据污染。
- 已有 105 条真实建模任务能正常显示。

页面验收：

- `/modeling` 正常。
- 款式看板正常。
- 项目建模进度正常。
- 产品组工作指引新增款式后，建模排期能看到。

关键业务验收：

- 原画未过审不能直接开始建模，除非有审批备注。
- 换建模师保留历史。
- 外包和内部建模师可以同时存在。

### 回滚

- 旧 `ModelingTask.styleName`、`styleCode` 保留，所以旧页面可回退。
- 若迁移生成的 `Style` 有问题，可以清空 `Style` 和 `styleId` 后重跑迁移脚本。
- 高风险迁移前必须备份数据库。

## 阶段 3：补产品组工作指引事实结构

目标：让产品组工作指引成为真正的执行事实入口。

### Prisma 新增模型

新增：

- `TaskCompletionRequirement`

可选新增：

- `TaskProgressEvent`

P0 也可以选择继续复用 `ProgressUpdate` 并补字段。

### Prisma 修改模型

修改 `ProjectTask`，新增字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `progressStatus` | `String?` | 当前进度下拉 |
| `lastProgressUpdatedAt` | `DateTime?` | 最近普通进度更新时间 |
| `lastKeyEventAt` | `DateTime?` | 最近关键节点时间 |

修改 `ProgressUpdate`，建议新增：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `eventType` | `String?` | 进度更新、送审、通过、驳回等 |
| `eventAt` | `DateTime?` | 事件发生时间 |
| `attachmentUrl` | `String?` | 附件 |

### 数据迁移动作

- 将现有 `ProjectTask.lastUpdatedAt` 复制到 `lastProgressUpdatedAt`。
- 已完成任务可根据 `actualFinishDate` 生成一条完成事件。
- 有 `progressNote` 的任务可生成普通进度事件。

### 导入脚本动作

任务实际进度 Excel 导入需要支持：

- 写 `ProjectTask.actualFinishDate`。
- 写 `ProjectTask.expectedFinishDate`。
- 写 `ProjectTask.status`。
- 写 `ProjectTask.progressStatus`。
- 写 `ProjectTask.blockReason`。
- 生成 `ProgressUpdate` / `TaskProgressEvent` 历史。

### 页面动作

产品组工作指引：

- 每个任务点击完成时，按 `TaskCompletionRequirement` 校验字段。
- 完成日期默认当天，可手动改。
- 原画任务完成时要求 PNG / JPG。
- 未完成任务可填预计完成日期、当前进度、阻塞原因、备注。
- 3 天未更新提醒根据 `lastProgressUpdatedAt` 和 `lastKeyEventAt` 判断。

项目排期：

- 预测输入读取这些执行事实。
- 重新测算后才更新预测结果。

### 验收

- 产品组工作指引能更新任务事实。
- 每次更新都留下历史。
- 进行中超过 3 天无更新能提醒。
- 任务完成后排期页面能看到事实变化。
- 重新测算后预测视图变化合理。

### 回滚

- 旧 `ProjectTask` 事实字段仍保留。
- 如果新事件记录异常，可暂时关闭事件读取，仍从 `ProjectTask` 主字段读取。

## 阶段 5：清理旧字段和技术债

此阶段暂缓，至少等内部测试稳定后再做。

可清理对象：

| 对象 | 处理 |
| --- | --- |
| `Project.ipName` | 结构化稳定后可废弃 |
| `Project.licensorName` | 结构化稳定后可废弃 |
| `Project.productType` | 结构化稳定后可废弃 |
| `Project.styleCount` | 迁移到 `expectedStyleCount` |
| `User.weeklyCapacityStyles` | 停用后可删除 |
| `ModelerCapabilityTag` | 暂时废弃，后续确认无用再删除 |
| `User.roleTitle` | 角色迁移稳定后可只作为显示备注 |
| `TaskRule` | 如果任务模板复杂，再拆为 `TaskDefinition`、`TaskTemplate`、`TaskTemplateItem` |

不建议 P0 做删除迁移。

## 每阶段通用执行流程

每个阶段执行前：

1. 确认当前分支是 `staging` 或专门的迁移分支。
2. 确认工作区没有未理解的代码改动。
3. 备份本地数据库。
4. 备份 staging 数据库。
5. 记录关键表数量。
6. 新建 Prisma migration。
7. 写数据迁移脚本。
8. 本地运行迁移。
9. 本地跑数据迁移脚本。
10. 本地验证页面和导入。
11. 提交代码。
12. 部署 staging。
13. 在 staging 备份后运行迁移。
14. staging 验收。

每个阶段执行后：

- 更新总控文档。
- 输出模块交接总结。
- 记录已执行迁移名。
- 记录数据备份路径。
- 记录已知问题和下一阶段注意事项。

## 通用测试清单

每个阶段至少测试：

- `npm run lint`
- `npm run build`
- `/api/health`
- `/` 项目排期页面
- `/product-guide` 产品组工作指引
- `/modeling` 建模排期
- `/users` 用户数据
- 登录和退出
- viewer 不能写业务数据
- manager 能写业务数据
- admin 能写用户数据

数据测试：

- 项目数量没有异常减少。
- 建模任务数量没有异常减少。
- 用户数量没有异常减少。
- 最新排期结果仍能读取。
- Excel 导入不会误删建模数据和用户数据。

回归样本：

- 小鸟4代：延期完成口径。
- 兔老大表情包mini：前置任务填表错误识别。
- 无牙仔猫猫：启动晚导致整体预测晚。
- 插画小人mini2代：任务 10 已开始但任务 7 未完成的异常。

## 推荐下一步实际工程

建议真正动数据库前，先做阶段 0：

- 写一个迁移前数据统计脚本。
- 写一个数据库备份说明。
- 在本地和 staging 各跑一次。
- 不改 schema。

阶段 0 完成后，再开始阶段 1 的主数据迁移。
