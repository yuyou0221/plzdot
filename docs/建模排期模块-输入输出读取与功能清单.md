# 建模排期模块：输入、输出、读取、对外可读信息与功能清单

更新时间：2026-05-30

本文用于固定建模排期模块的开发边界。后续开发前，优先以本文作为模块口径；如果业务口径变化，先修改本文，再修改代码。

## 1. 模块定位

建模排期负责款式级建模任务。

它管理：

- 款式级 ModelingTask 的生成与更新
- 建模师分配
- 外包状态
- 建模状态流转
- 建模计时：开始由建模侧触发，停止由系统自动生成
- 建模成果提交
- 产品检修 / 送审结果接收
- 反馈记录
- 项目级建模进度计算
- 给项目排期和产品组工作指引的建模事实输出

它不管理：

- 项目规划基线
- 项目计划上线日期
- 项目整体预测计算
- 人员基础资料
- 外包供应商基础资料
- 产品组款式资料录入入口
- 财务、知识库、权限、送审 AI

## 2. 四类边界定义

### 2.1 输入

输入指外部模块主动提交给建模排期的信息。

建模排期收到输入后，可以创建或更新自己的建模数据。

### 2.2 输出

输出指建模排期主动写回、通知或生成给其他模块使用的建模事实事件。

输出只包含主动事件，不包含其他模块主动读取的状态、列表、进度和统计。

建模排期输出的是事实事件，不直接修改项目规划基线。

### 2.3 读取

读取指建模排期主动从其他模块读取基础数据。

读取的数据只用于展示、计算和辅助决策，建模排期不维护这些基础数据。

### 2.4 对外可读信息

对外可读信息指其他模块可以读取建模排期维护的数据。

其他模块可以展示这些信息，但不应直接写建模排期状态。

## 3. 输入

### 3.1 来自产品组工作指引的输入（基础完成）

产品组工作指引只提交执行事实和款式基础资料，不维护建模师、外包、建模状态、产能和建模排期结果。

#### 3.1.1 款式清单提交与建模确认

触发时机：

- 原画里程碑完成后
- 产品组弹出较大的“系列建模款式清单”界面
- 用户填写一个系列的完整款式清单后提交给建模排期

系列口径：

- 款式清单以“系列”为整体提交、整体确认、整体退回、整体重新提交
- 一个系列有几款，就提交几款、审核几款、退回几款、重新提交几款
- 第一版不做单款部分确认；建模侧确认 / 退回均针对当前系列整批处理
- 被退回后，产品组重新提交时必须重新提交该系列完整款式清单，不能只提交被页面草稿保留下来的部分款式

每一行款式至少包含：

| 字段 | 说明 |
| --- | --- |
| projectId | 项目 ID |
| projectTaskId | 对应任务 7 或任务 10 |
| taskNo | 只接受 7 或 10 |
| sourceStyleId | 产品组来源款式 ID，可选但推荐 |
| styleCode | 真实业务款式编号；测试自动编号不得作为业务编号展示 |
| styleSequence | 款式序号 |
| styleName | 款式名称 |
| isRequired | 是否必做 |
| isFirstModelingStyle | 是否第一款建模款式 |
| difficulty | 难度 |
| estimatedWorkdays | 预计建模天数 |
| originalArtApprovedDate | 原画过审日期 |
| referenceImageUrls | 原画图 / 参考图 URL |
| notes | 备注 |

规则：

- 必须且只能有 1 个 `isFirstModelingStyle = true`
- 第一款后续由任务 7 启动
- 其他款式后续由任务 10 启动
- 产品组提交后，建模排期先生成或更新待确认的 ModelingTask
- 建模排期需要有“款式清单确认”动作
- 建模确认后，款式任务才正式进入建模排期管理
- 建模确认前，款式清单可以作为待确认数据展示，但不进入正式产能计算
- 建模确认前，不允许分配建模师、开始计时、提交成果或进入送审流程
- 款式清单提交后，建模排期生成专属任务待办：`款式清单待确认`
- 该待办不使用通用 `WorkTask`，由建模款式状态推导；存在 `待确认` 款式时显示，确认或退回后自动消失
- 待办条只作为入口，点击后打开同一张系列款式清单页
- 确认 / 退回补充动作只能在系列款式清单页内执行
- 建模确认后，默认状态为 `未启动`
- 提交款式清单不代表建模开始
- 提交款式清单不代表全部款式进入 `未分配`
- 待确认 / 退回补充状态不进入正式建模进度和产能统计
- 每次款式清单提交都会记录 `styleSubmissionBatchId` 和 `styleSubmissionVersion`
- 同一个退回补充系列重新提交时，必须包含原系列完整款式，不能通过缺失静默删除款式
- 如果任务 7 / 10 已经启动，后续补充确认的新款式在确认后直接进入 `未分配`

建模确认时需要核对：

| 核对项 | 说明 |
| --- | --- |
| 款式数量 | 产品组提交的款式数量是否完整 |
| 款式名称 / 序号 | 是否能支持后续建模沟通和排期 |
| 第一款标记 | 是否必须且只有一款 `isFirstModelingStyle = true` |
| 任务归属 | 第一款对应任务 7，其余款对应任务 10 |
| 是否必做 | 是否影响项目排期回写 |
| 难度 / 预计天数 | 是否可用于产能测算 |
| 原画过审信息 | 是否满足进入建模的前置条件 |
| 参考图 / 原画图 | 是否足够建模使用 |

确认结果：

| 确认结果 | 处理方式 |
| --- | --- |
| 确认通过 | 当前系列全部款式正式生效，默认状态为 `未启动`；如果对应任务 7 / 10 已启动，补充款式直接进入 `未分配` |
| 退回补充 | 当前系列全部款式不进入正式建模排期，必须填写退回原因，并回传产品组补充 |
| 部分确认 | 第一版不支持；后续如果要做，需重新确认产品组与建模排期边界 |

退回后重新提交：

- 退回状态为 `退回补充`
- 退回原因写入 `ModelingFeedback`
- 重新提交后，同一系列完整款式清单回到 `待确认`
- 重新提交不会漏掉原系列中的其他款式
- 如果重新提交缺少原系列款式，接口会拒绝，并提示应走单独取消事件
- 已经推进到正式建模流程的款式，不应被重新提交静默重置状态

确认后需要回传产品组：

- 已确认的款式列表
- 未确认 / 退回补充的款式列表
- 退回原因
- 款式清单提交批次：`styleSubmissionBatchId`
- 款式清单版本：`styleSubmissionVersion`
- 建模排期生成的 `modelingTaskId`
- 产品组来源款式 ID：`sourceStyleId`
- 对应项目任务：`projectTaskId`
- 对应任务编号：`taskNo`
- 款式序号 / 款式名 / 款式编号
- 是否第一款：`isFirstModelingStyle`
- 是否必做：`isRequired`
- 原画图 / 参考图：`referenceImageUrls`
- 原画过审信息：`originalArtStatus`、`originalArtApprovedDate`
- 难度和预计建模天数
- 每个款式当前建模状态

这份返回清单是给产品组程序保存映射用的正式款式级任务清单。产品组后续应优先使用 `modelingTaskId` 调用建模排期读取、审核和送审结果接口，不应再靠款式名反查。

测试字段：

- 测试模拟器或 fixture 自动生成的字段，例如 `FIX-64974370-S01`、`LOCAL-...`、`RESUBMIT-...`、`fixture-...`，统一称为“测试字段”
- 测试字段只给 `admin` 展示
- 非 `admin` 不应在页面、清单、详情、原始输出中看到这些测试字段
- 测试字段用于本地模拟、接口匹配和调试，不等同于真实业务款式编号
- 如果产品组传入真实 `styleCode`，且不是测试字段格式，可以作为业务款式编号展示

#### 3.1.2 建模任务启动事件

任务 7 启动：

- `taskNo = 7`
- `startScope = first-style`
- 建模排期将第一款从 `未启动` 推进到 `未分配`
- 只影响 `isFirstModelingStyle = true` 的款式

任务 10 启动：

- `taskNo = 10`
- `startScope = remaining-styles`
- 建模排期将其余款式从 `未启动` 推进到 `未分配`
- 只影响 `isFirstModelingStyle = false` 的款式

任务 8、9：

- 不启动款式级建模任务
- 建模排期接口应拒绝非 7 / 10 的 taskNo

启动规则：

- 只有已经由建模侧确认、且状态为 `未启动` 的款式可以启动
- `待确认` / `退回补充` 款式不能启动
- 已经启动、已通过、暂停或取消的款式不会被重复启动
- 重复启动必须幂等：不重复生成任务，不重复改写状态
- 启动事件只改变款式状态，不分配建模师，不开始建模计时
- 启动事件不修改项目排期规划基线

启动成功后需要返回：

- `projectId`
- `projectTaskId`
- `taskNo`
- `startScope`
- `targetCount`
- `startedCount`
- `skippedCount`
- `styles`
- `skippedStyles`

其中 `styles` 需要包含每款的 `modelingTaskId`、`sourceStyleId`、`styleSequence`、`styleName`、`isFirstModelingStyle`、`isRequired`、`previousStatus`、`modelingStatus`、`startResult` 和 `skipReason`。这份返回用于产品组程序确认启动事件是否被建模排期正确接收。

#### 3.1.3 产品审核 / 送审结果

前置条件：

- 建模排期必须先收到建模侧提交的建模成果
- 建模成果提交后，款式状态进入 `待验收`
- 产品组审核必须针对最近一次建模成果提交，使用 `submissionFeedbackId` / `feedbackId` 锁定提交记录
- 如果产品组传入的 `submissionFeedbackId` 不是最新提交，建模排期应拒绝，避免错审旧成果
- 产品组只能对 `待验收` 款式提交内部审核结果
- 产品组只能对 `待送审` / `已送审` / `等反馈` 款式提交版权方送审结果
- 未提交建模成果的款式不能直接写入内部审核或版权方送审结果

产品组可以提交：

- 内部通过可送审
- 内部不通过
- 已送审
- 等反馈
- 送审通过
- 送审不通过

状态映射：

| 产品组输入 | 建模排期状态 | 反馈要求 | 计时规则 |
| --- | --- | --- | --- |
| 内部通过可送审 | 待送审 | 可不填文字，允许附件 | 结束正在运行的建模计时 |
| 内部不通过 | 排队中 | 必须有文字反馈，附件可选 | 不结束正在运行的建模计时 |
| 已送审 | 已送审 | 可不填文字，允许附件 | 不结束正在运行的建模计时 |
| 等反馈 | 等反馈 | 可不填文字，允许附件 | 不结束正在运行的建模计时 |
| 送审通过 | 已通过 | 可不填文字，允许附件 | 结束正在运行的建模计时 |
| 送审不通过 | 排队中 | 必须有文字反馈，附件可选 | 不结束正在运行的建模计时 |

附件类型：

- 图片反馈
- PDF 反馈
- PPT 反馈

第一版请求字段：

```ts
feedbackAttachments?: {
  imageUrl?: string | null;
  pdfUrl?: string | null;
  pptUrl?: string | null;
};
```

为了兼容简单链接，也允许传 `attachmentUrls: string[]`。建模排期会把结构化附件写入反馈内容摘要，并在接口返回 `feedbackAttachments` 和 `attachmentUrls`，方便产品组展示或保存映射。

建模成果提交需要回传给产品组：

- `eventType = modeling_work_submitted`
- `projectId`
- `projectTaskId`
- `modelingTaskId`
- `sourceStyleId`
- 款式编号 / 款式序号 / 款式名称
- `modelingStatus = 待验收`
- `feedbackId`
- `submissionFeedbackId`
- `reviewRound`
- 提交人
- 提交时间
- 成果说明
- 成果链接
- 递交前状态：`submittedFromStatus`
- 驳回恢复目标：`restoreStatusOnRejection = 排队中`
- 本轮递交累计工时：`submittedWorkMinutes`
- 递交快照：`submissionSnapshot`

递交快照保存规则：

- 递交快照写在本次 `ModelingFeedback` 的 `submissionSnapshot`
- 记录递交前状态、建模师、外包状态、外包供应商、累计工时、是否正在计时、成果说明、成果链接、递交人、递交时间和轮次
- 产品组驳回后，建模排期按快照恢复到可继续工作的状态，第一版统一恢复为 `排队中`
- 驳回恢复时不得清除建模师、外包供应商、累计工时、成果记录和历史反馈

### 3.2 来自建模组的输入

建模组可以录入：

| 字段 / 动作 | 是否允许 | 说明 |
| --- | --- | --- |
| 分配给谁 | 可以 | 写入 `modelerId`，状态由系统自动从未分配推进到已排期 |
| 是否外包 | 可以 | 写入 `isOutsourced` |
| 外包供应商 | 可以 | 写入 `outsourceVendorId`，状态由系统自动推进到外包中 |
| 预计建模天数 | 不可以 | 来自款式清单 / 管理侧基础资料，建模侧只读 |
| 状态推进 | 不可以手动填写 | 由代码根据分配、外包、计时、提交成果、产品审核 / 送审结果自动生成 |
| 开始建模计时 | 可以 | 建模侧点击开始；开始另一款时，系统自动停止同一建模师正在计时的其他款式 |
| 停止建模计时 | 不可以手动填写 | 由代码在开始其他款式或提交建模成果时自动生成 |
| 提交建模成果 | 可以 | 进入产品组检修入口，状态自动变为 `待验收` |
| 成果说明 | 可以 | 随建模成果提交写入本轮提交记录 |
| 成果链接 | 可以 | 随建模成果提交写入本轮提交记录 |
| 剩余工时 | 可以 | 写入 `remainingWorkdays`，按工作日填写 |
| 备注 | 可以 | 写入 `ModelingTask.notes`，仅作为建模侧备注，不等同于检修 / 送审反馈 |

建模组不能录入：

- 产品检修反馈
- 版权方反馈
- 内部通过 / 不通过结论
- 送审通过 / 不通过结论

检修 / 送审记录由产品组或管理侧写入，建模师只能阅读。

## 4. 读取

### 4.1 读取用户数据

建模排期读取：

- 可排期建模师
- 人员每周可用工作日
- 是否可排期
- 擅长类型
- 请假 / 不可用信息
- 稳定外包供应商基础信息

建模排期不维护：

- 人员姓名
- 人员状态
- 组织架构
- 账号权限
- 外包供应商基础资料

### 4.2 读取项目排期的对外可读信息

建模排期读取项目排期提供的对外可读信息，用于判断哪些项目进入建模窗口、哪些建模里程碑本月 / 下月 / 逾期。

需要字段：

| 字段 | 是否需要 | 说明 |
| --- | --- | --- |
| projectId | 需要 | 项目唯一 ID |
| 项目名称 | 需要 | 用于展示和匹配 |
| 项目状态 / 当前阶段 | 需要 | 项目进入原画阶段时，建模排期需要开始关注 |
| 建模负责人 | 需要 | 项目级建模负责人，不等于每个款式的建模师 |
| 任务编号 7-10 里程碑信息 | 需要 | 建模相关里程碑 |
| 任务编号 7-10 的 projectTaskId | 需要 | 最重要的任务级读取字段 |
| 任务编号 7-10 的状态 | 需要 | 用于判断是否启动、逾期、完成 |
| 是否延期 / 风险等级 | 需要 | 用于管理层和预警展示 |

任务编号规则：

- 任务 7：产生 1 个款式级建模任务
- 任务 10：产生至少 1 个款式级建模任务
- 任务 8、9：支线任务，不产生款式级建模任务

建模排期不直接修改：

- 规划视图
- 计划开始 / 完成
- 计划上线日
- 项目整体预测

### 4.3 读取产品组工作指引

建模排期不主动维护产品组工作指引的数据。

建模排期可以读取或接收：

- 款式清单
- 原画图 / 参考图
- 原画过审日期
- 产品类型
- 产品组提交的审核 / 送审结果

## 5. 输出

本章只记录建模排期主动输出的事件。其他模块主动读取的状态、列表、进度、统计均归入第 6 章“对外可读信息”。

### 5.1 输出给产品组工作指引（基础完成）

建模排期主动输出给产品组工作指引的事件：

| 事件 | 触发时机 | 产品组用途 |
| --- | --- | --- |
| `style_list_confirmed` | 建模侧确认款式清单 | 产品组保存 `sourceStyleId` 与 `modelingTaskId` 的正式映射 |
| `style_list_returned` | 建模侧退回款式清单 | 产品组提示用户补充 / 重新提交完整系列款式清单 |
| `modeling_work_submitted` | 建模师提交建模成果，款式进入 `待验收` | 产品组生成内部审核待办 |

事件保存规则：

- 三个事件都会随当前接口直接返回
- 三个事件都会写入 `ModelingProductGuideEvent`
- 产品组如果没有接住当前接口返回，可以通过事件补读接口读取
- `modeling_project_all_approved` 不属于 5.1 主动输出事件，只作为 6.1 / 6.2 的可读完成事实

不属于 5.1 输出、应归入 6.1 对外可读信息的内容：

- 款式列表
- 每款建模状态
- 建模师 / 外包供应商
- 最新反馈和修改轮次
- 是否卡住 / 是否需要产品美术处理
- 项目建模进度
- 是否全部通过
- 项目必做款式是否全部 `已通过`

### 5.2 输出给项目排期（后续阶段）

本阶段暂不定义给项目排期的主动输出事件。

项目排期需要的建模整体进度、必做款式是否全部通过、最后一款通过日期、是否满足“根据效果图建模”完成条件、延期风险、产能不足、送审 / 反馈卡住、是否需要重新测算、回写项目任务完成事实草稿，均归入 6.2 对外可读信息。

回写原则：

- 所有必做 ModelingTask 均为 `已通过`
- 才允许将项目任务“根据效果图建模”视为完成
- 部分款式完成不能推进后续任务
- 高风险回写先做确认 / 草稿，不静默覆盖项目排期数据

### 5.3 输出给管理层（后续阶段）

## 7. 状态口径

### 7.1 核心原则

- 建模状态由业务事件触发，不允许建模组手动填写状态。
- `建模中` 表示款式处于建模制作阶段，不等同于当前正在计时。
- 当前是否正在计时以 `activeWorkStartedAt` 为准。
- 停止计时由程序触发，不提供建模师手动停止入口。
- 产品检修 / 版权方送审结论只由产品组或管理侧写入，建模师只能阅读。

### 7.2 当前状态清单

| 状态 | 说明 |
| --- | --- |
| 待确认 | 产品组已提交款式清单，但建模侧尚未确认 |
| 退回补充 | 建模侧认为款式清单信息不足，退回产品组补充 |
| 未启动 | 款式清单已确认，但任务 7/10 尚未启动 |
| 未分配 | 已由任务 7/10 启动，但未分配建模师或外包 |
| 已排期 | 已分配建模师，等待开始建模 |
| 排队中 | 等待建模师继续处理，常用于审核 / 送审驳回后重新排队 |
| 建模中 | 建模师正在制作或已进入制作阶段；是否正在计时看 `activeWorkStartedAt` |
| 修改中 | 保留兼容旧数据和后续细分需求；第一版产品驳回统一回到 `排队中` |
| 待验收 | 建模师已提交成果，等待产品美术检修 |
| 待送审 | 内部通过，可提交版权方 |
| 已送审 | 已提交版权方 |
| 等反馈 | 等待版权方反馈 |
| 已通过 | 版权方过审或确认完成 |
| 外包中 | 已交外包制作 |
| 暂停 | 临时暂停 |
| 取消 | 款式取消 |

### 7.3 事件驱动流转

| 事件 | 触发方 | 前置状态 | 结果状态 | 备注 |
| --- | --- | --- | --- | --- |
| `style_list_confirmed` | 建模侧确认 | 待确认 | 未启动 | 按系列整批确认 |
| `style_list_returned` | 建模侧退回 | 待确认 | 退回补充 | 必须填写退回原因 |
| `style_start_event_first_style` | 产品组任务 7 启动事件 | 未启动 | 未分配 | 只启动第一款 |
| `style_start_event_remaining_styles` | 产品组任务 10 启动事件 | 未启动 | 未分配 | 启动其余款式 |
| `assign_modeler` | 建模排期 / 管理侧 | 未分配 / 排队中 | 已排期 | 只写建模师，不开始计时 |
| `mark_outsourced` | 建模排期 / 管理侧 | 未分配 / 排队中 / 已排期 | 外包中 | 外包不记录个人计时 |
| `start_work_timer` | 建模师 | 已排期 / 排队中 / 建模中 / 修改中 | 建模中 | 同一建模师其他运行计时自动停止 |
| `modeling_work_submitted` | 建模师 | 已排期 / 排队中 / 建模中 / 修改中 / 外包中 | 待验收 | 自动停止本款运行计时，并输出给产品组 |
| `internal_review_approved` | 产品组 / 管理侧 | 待验收 | 待送审 | 可不填文字反馈 |
| `internal_review_rejected` | 产品组 / 管理侧 | 待验收 | 排队中 | 必须填写文字反馈 |
| `copyright_review_submitted` | 产品组 / 管理侧 | 待送审 | 已送审 | 已通过审核 / 送审结果入口支持 |
| `copyright_review_waiting` | 产品组 / 管理侧 | 已送审 / 待送审 | 等反馈 | 已通过审核 / 送审结果入口支持 |
| `copyright_review_approved` | 产品组 / 管理侧 | 待送审 / 已送审 / 等反馈 | 已通过 | 可不填文字反馈 |
| `copyright_review_rejected` | 产品组 / 管理侧 | 待送审 / 已送审 / 等反馈 | 排队中 | 必须填写文字反馈 |
| `pause_style` | 管理侧 | 非终态 | 暂停 | 后续阶段细化 |

### 7.4 计时停止规则

| 触发事件 | 是否自动停止计时 | 说明 |
| --- | --- | --- |
| 同一建模师开始另一款 | 是 | 旧款 `activeWorkStartedAt` 清空，分钟数累计到 `actualWorkMinutes` |
| 建模师提交成果 | 是 | 本款进入 `待验收`，递交时累计本轮分钟数 |
| 分配给其他建模师 | 是 | 防止旧建模师计时继续运行 |
| 标记为外包 | 是 | 外包不记录个人建模计时 |
| 内部通过可送审 | 防御性停止 | 正常情况下提交成果时已停止；如遗留计时仍在运行，接口应清理 |
| 送审通过 | 防御性停止 | 正常情况下提交成果时已停止；如遗留计时仍在运行，接口应清理 |
| 取消款式 | 是 | 款式取消后不得继续计时 |
| 已通过款式重开 | 防御性停止 | 正常情况下已通过款式没有运行计时；如遗留计时仍在运行，接口应清理 |
| 内部不通过 | 否 | 状态回到 `排队中`，等待建模师重新开始或继续 |
| 送审不通过 | 否 | 状态回到 `排队中`，等待建模师重新开始或继续 |
| 手动停止计时 | 不允许 | API 应拒绝 `action=stop` |

## 8. 产能和提醒规则

当前规则：

- 一般款：约 7 个工作日
- 简单款：约 4 个工作日
- 最简单换色款：约 1 个工作日
- 困难正比例款：约 20 个工作日
- 长期稳定外包可以算入产能
- 外包供应商不做个人产能记录，只记录任务状态和实际用时
- 一个人手头工时超过 24 个工作日即超载
- 建模中超过 3 天没有更新需要提醒
- 同一建模师同时只能有一个正在运行的计时
- 开始另一个款式时，应自动停止同一建模师其他正在运行的计时
- 建模工时按分钟累计
