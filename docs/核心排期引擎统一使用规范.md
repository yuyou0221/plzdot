# 核心排期引擎统一使用规范

最后更新：2026-07-06

这份文档用于约束所有模块统一使用排期引擎，避免项目排期、产品组工作指引、建模排期、周月任务、财务测算各自解释一套逻辑。

## 最高规则

```text
项目排期脚本 = 平台唯一排期测算真相
不经过排期内核，就拿不到合法的排期结果。
不写入执行事实，就不能影响预测。
不重新测算，就不能声称预测已经更新。
```

## 唯一排期内核

当前核心脚本：

```text
src/lib/schedule-engine/core/project-schedule-core.js
src/lib/schedule-engine/core/project-analysis-v5-excel.js
```

这些脚本决定：

- 任务编号。
- 任务依赖。
- 标准天数。
- 里程碑分组。
- 任务状态。
- 后置任务推断完成。
- 计划视图。
- 预测视图。
- 延期完成。
- 任务 7-10 建模里程碑。
- 任务 30 首批大货生产。
- 任务 31 详情页设计。
- 周度 / 月度任务分析。

任何模块不得重新发明这些规则。

## 统一调用层

所有模块触发排期测算时，只能通过：

```text
src/lib/schedule-engine/service.ts
src/lib/schedule-engine/port.ts
src/lib/schedule-engine/project-analysis-v5-port.ts
src/lib/schedule-engine/project-analysis-v5-input.ts
```

其中：

- `service.ts` 是业务层唯一测算入口。
- `port.ts` 定义 `ScheduleEnginePort` 和 `ScheduleEnginePayload` 契约。
- `project-analysis-v5-port.ts` 把当前 v5 JS 内核封装为端口实现。
- `project-analysis-v5-input.ts` 负责从数据库读取项目、任务事实、任务规则并转换成 v5 内核输入。
- `adapters.ts` 只负责把端口输出持久化为平台数据库结果。

所有模块读取排期结果时，应优先通过：

```text
src/lib/schedule-repository.ts
ScheduleProjectResult
ScheduleTaskResult
```

- `schedule-repository.ts` 负责把数据库排期结果整理成项目排期页面可用的数据。
- `ScheduleProjectResult` 是项目级结果。
- `ScheduleTaskResult` 是任务级结果。

其他模块不要直接读脚本内部中间变量，也不要自己用原始字段重新推导排期状态。

## V5 日期语义

排期内核输出的日期字段必须区分业务含义，不能混用：

| 字段 | 定义 |
| --- | --- |
| `projectStartDate` | 项目启动日期，是生成管理计划 `planned` 的起点。正式测算不再用上线日期倒推一个假启动日兜底。 |
| `plannedLaunchDate` | 用户填写的计划上线 / 出货日期。 |
| `effectiveLaunchDate` | 用于计算的上线日期。如果计划上线日落在不可排期日，由既有排期日规则顺延。 |
| `projectedLaunchDate` | 当前预测上线日期。等于 `max(effectiveLaunchDate, earliestReadyDate)`，不早于计划上线日期。 |
| `earliestReadyDate` | 项目当前最早可完成日期，等于 `max(#30 calculatedFinishDate, #31 calculatedFinishDate)`，用于诊断“项目已经准备好”和“计划上线日期”之间的差异。 |
| `plannedStartDate` / `plannedFinishDate` | 从 `projectStartDate` 正推得到的管理计划日期。 |
| `latestStartDate` / `latestFinishDate` | 从 `effectiveLaunchDate` 倒推得到的原始最晚安全日期。 |
| `currentLatestStartDate` / `currentLatestFinishDate` | 从 `projectedLaunchDate` 倒推得到的动态最晚安全日期。 |
| `calculatedStartDate` / `calculatedFinishDate` | 当前可达预测日期。基于真实完成、真实开始、预计完成、剩余天数和前置任务 calculated 结果传播，可以早于、等于或晚于 planned。 |
| `actualStartDate` / `actualFinishDate` | 真实执行事实。实际完成日期必须覆盖本任务的 `calculatedFinishDate`。 |

差异字段：

| 字段 | 定义 |
| --- | --- |
| `floatDays` | `latestFinishDate - plannedFinishDate`，表示管理计划与最晚安全线之间的缓冲。 |
| `planDeltaDays` | `calculatedFinishDate - plannedFinishDate`，表示当前预测比管理计划晚几天。 |
| `deadlineRiskDays` | `calculatedFinishDate - latestFinishDate`，表示是否已经影响原计划上线。 |
| `currentDeadlineRiskDays` | `calculatedFinishDate - currentLatestFinishDate`，表示是否继续影响当前预测上线。 |
| `currentDdlDate` | 兼容旧字段，当前等价于 `calculatedFinishDate`，不是最晚安全日期。 |

判断口径：

- `planned` 必须从项目启动日正推，不得承载上线日期倒推结果。
- `latest` 才能来自上线日期倒推。
- 已完成任务：`calculatedFinishDate = actualFinishDate`，并用该实际完成日拉早或推迟下游。
- 已完成任务如果早于模型依赖约束，事实仍优先，但输出 `calculationWarnings` 诊断，例如 `actual_finish_before_finish_after_constraint`。
- 进行中任务：`calculatedStartDate = actualStartDate`，即使早于 planned 也必须进入 calculated。
- 进行中任务如果填写 `remainingDays`，本任务完成日优先按 `today + remainingDays`，可以早于标准工期。
- 进行中任务如果填写未来 `expectedFinishDate`，本任务完成日优先按该预计完成日，可以早于标准工期。
- 未完成任务即使填写了 `expectedFinishDate`，只要该预计完成日早于 `today`，也不能把它作为最终 `calculatedFinishDate`。
- 未开始任务如果有 startAfter 前置，`calculatedStartDate` 优先来自前置任务的 `calculatedFinishDate + lag`，可以早于 planned；但如果该日期早于 `today` 且没有实际开始事实，则从 `today` 开始预测。
- 未开始任务如果没有 startAfter 前置，仍从 planned 开始；如果 planned 已经早于 `today`，则从 `today` 开始预测。
- `finishAfter` 仍是硬完成约束：预计完成、剩余天数和标准工期都不能让未完成任务早于 finishAfter 约束完成。
- 空 `remainingDays` 表示未填写，不能按 0 天处理。
- actual 输入的最低匹配条件是系统项目 ID + 任务编号；`taskName` 缺失时从任务规则回填，不得直接丢弃 actual。
- 同项目同任务多条 actual 按更新时间判断新旧，并按字段取最新非空事实，避免旧 actualStartDate 误导排序，也避免新空值覆盖旧事实。
- 页面和其他模块只消费这些正式字段，不重新推导风险。

## 路线 A / B 的 #17 与 #21 口径

- 红蜡路线 A：#17 红蜡确认保持原有 21 个工作日，#17 等待 #14 / #15，#21 仍等待 #17 / #12。
- 手板路线 B：#17 红蜡确认 / 手板确认工期为 10 个工作日，#17 等待 #18，#21 仍等待 #17 / #12。
- 手板路线 B 不是“#21 不等 #17”。后续对 #21 依赖的任何修改，都必须另行确认业务口径。
- 本口径只影响排期内核任务图，不改变 #21、#30、#31 工期。

## 为什么不要直接复制 milestoneByTaskNo

`milestoneByTaskNo` 看起来很小，复制一份似乎没问题，但它实际代表平台对任务编号的统一解释。

当前口径是：

| 里程碑 | 任务编号 |
| --- | --- |
| 原画里程碑 | 1-6 |
| 建模里程碑 | 7-10 |
| 红蜡里程碑 | 11-15、17、18 |
| 平面里程碑 | 16、19、20、28、29、31 |
| 产前里程碑 | 21-27 |
| 大货里程碑 | 30 |

如果复制多份，后续只要有一处没同步，就会出现同一个项目在不同页面里程碑不同的问题。

具体风险：

- 项目排期认为任务 31 是平面里程碑，产品组工作指引却把它当大货里程碑。
- 建模排期认为任务 7-10 是建模里程碑，但项目详情页只算 7、10，漏掉 8、9。
- 财务测算读取大货时间时把任务 31 也算进去，但上线日历只看任务 30。
- 后续脚本调整任务编号或里程碑分组时，只改了一份，其他模块继续用旧规则。

所以规则不是不能写，而是只能有一个来源：

```text
src/lib/schedule-domain/milestones.ts
```

其他地方只能 import：

```ts
import { milestoneByTaskNo } from "@/lib/schedule-domain";
```

## 模块使用边界

### 项目排期

可以：

- 读取 `ScheduleProjectResult`。
- 读取 `ScheduleTaskResult`。
- 展示规划视图、预测视图、上线日历。
- 触发重新测算。

不可以：

- 自己定义任务编号规则。
- 自己定义里程碑分组。
- 不重新测算就声明预测已更新。

### 产品组工作指引

可以：

- 写入任务完成、预计完成、阻塞、备注。
- 写入款式清单和原画状态。
- 读取统一排期结果生成工作指引。

不可以：

- 自己判断项目是否延期。
- 自己改变规划视图。
- 自己推算预测上线。

### 建模排期

可以：

- 写入款式级建模状态、分配、外包、反馈。
- 读取任务 7-10 的统一结果判断建模里程碑。
- 在任务 7 / 10 的全部必做真实款式通过后，提供项目排期可读取的建模完成事实。

不可以：

- 自己重算项目上线。
- 主动回写项目排期。
- 修改 `ProjectTask` 完成事实。
- 用虚拟款式生成项目任务完成事实。

### 财务测算

可以：

- 读取项目预测上线日期。
- 读取项目延期天数。
- 读取项目当前风险状态。

不可以：

- 自己推研发周期。
- 自己解释任务依赖。

## 后续重构顺序

建议不要一次重构所有模块。顺序应是：

1. 先把纯函数规则收拢到 `src/lib/schedule-domain/`。
2. 再让 `adapters.ts` 和 `schedule-repository.ts` 使用这些规则。
3. 再让产品组工作指引读取统一领域层。
4. 再让建模排期读取统一领域层。
5. 最后再接财务测算。

每一步都要保证页面仍能打开，并用回归样本检查。
