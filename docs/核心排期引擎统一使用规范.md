# 核心排期引擎统一使用规范

最后更新：2026-05-25

这份文档用于约束所有模块统一使用排期引擎，避免项目排期、产品组工作指引、建模排期、周月任务、财务测算各自解释一套逻辑。

## 最高规则

```text
项目排期脚本 = 平台唯一排期测算真相
不经过排期内核，就拿不到合法的排期结果。
不写入执行事实，就不能影响预测。
不重新测算，就不能声称预测已经更新。
```

## 唯一排期内核

当前核心脚本：

```text
legacy/schedule-engine/project-schedule-core.cjs
legacy/schedule-engine/project-analysis-v5-excel.cjs
legacy/schedule-engine/generate-weekly-analysis.cjs
```

这些脚本决定：

- 任务编号。
- 任务依赖。
- 标准天数。
- 里程碑分组。
- 任务状态。
- 后置任务推断完成。
- 计划视图。
- 预测视图。
- 延期完成。
- 任务 7-10 建模里程碑。
- 任务 30 首批大货生产。
- 任务 31 详情页设计。
- 周度 / 月度任务分析。

任何模块不得重新发明这些规则。

## 统一读取层

所有模块读取排期结果时，应优先通过：

```text
src/lib/schedule-engine/adapters.ts
src/lib/schedule-repository.ts
ScheduleProjectResult
ScheduleTaskResult
```

其中：

- `adapters.ts` 负责把脚本输出持久化为平台数据库结果。
- `schedule-repository.ts` 负责把数据库排期结果整理成项目排期页面可用的数据。
- `ScheduleProjectResult` 是项目级结果。
- `ScheduleTaskResult` 是任务级结果。

其他模块不要直接读脚本内部中间变量，也不要自己用原始字段重新推导排期状态。

新增排期相关展示规则时，优先放这里，不要散落到各页面或各 repository。

## 为什么不要直接复制 milestoneByTaskNo

`milestoneByTaskNo` 看起来很小，复制一份似乎没问题，但它实际代表平台对任务编号的统一解释。

当前口径是：

| 里程碑 | 任务编号 |
| --- | --- |
| 原画里程碑 | 1-6 |
| 建模里程碑 | 7-10 |
| 红蜡里程碑 | 11-15、17、18 |
| 平面里程碑 | 16、19、20、28、29、31 |
| 产前里程碑 | 21-27 |
| 大货里程碑 | 30 |

如果复制多份，后续只要有一处没同步，就会出现同一个项目在不同页面里程碑不同的问题。

具体风险：

- 项目排期认为任务 31 是平面里程碑，产品组工作指引却把它当大货里程碑。
- 建模排期认为任务 7-10 是建模里程碑，但项目详情页只算 7、10，漏掉 8、9。
- 财务测算读取大货时间时把任务 31 也算进去，但上线日历只看任务 30。
- 后续脚本调整任务编号或里程碑分组时，只改了一份，其他模块继续用旧规则。

所以规则不是不能写，而是只能有一个来源：

```text
src/lib/schedule-domain/milestones.ts
```

其他地方只能 import：

```ts
import { milestoneByTaskNo } from "@/lib/schedule-domain";
```

## 模块使用边界

### 项目排期

可以：

- 读取 `ScheduleProjectResult`。
- 读取 `ScheduleTaskResult`。
- 展示规划视图、预测视图、上线日历。
- 触发重新测算。

不可以：

- 自己定义任务编号规则。
- 自己定义里程碑分组。
- 不重新测算就声明预测已更新。

### 产品组工作指引

可以：

- 写入任务完成、预计完成、阻塞、备注。
- 写入款式清单和原画状态。
- 读取统一排期结果生成工作指引。

不可以：

- 自己判断项目是否延期。
- 自己改变规划视图。
- 自己推算预测上线。

### 建模排期

可以：

- 写入款式级建模状态、分配、外包、反馈。
- 读取任务 7-10 的统一结果判断建模里程碑。
- 在全部必做真实款式通过后提示回写任务 10。

不可以：

- 自己重算项目上线。
- 静默回写项目排期。
- 用虚拟款式回写项目任务完成。

### 财务测算

可以：

- 读取项目预测上线日期。
- 读取项目延期天数。
- 读取项目当前风险状态。

不可以：

- 自己推研发周期。
- 自己解释任务依赖。

## 回归样本

已在代码中固化：

```text
src/lib/schedule-domain/regression-samples.ts
```

当前样本：

| 项目 | 检查点 |
| --- | --- |
| 小鸟4代 | 延期完成口径 |
| 兔老大表情包mini | 前置任务填表错误识别 |
| 无牙仔猫猫 | 启动晚导致整体预测晚 |
| 插画小人mini2代 | 任务 10 已开始但任务 7 未完成 |

每次改以下内容都要回归：

- 排期脚本。
- Excel 导入。
- `src/lib/schedule-domain/`。
- 项目排期展示。
- 产品组工作指引任务生成。
- 建模排期里程碑聚合。
- 财务测算项目周期读取。

## 后续重构顺序

建议不要一次重构所有模块。顺序应是：

1. 先把纯函数规则收拢到 `src/lib/schedule-domain/`。
2. 再让 `adapters.ts` 和 `schedule-repository.ts` 使用这些规则。
3. 再让产品组工作指引读取统一领域层。
4. 再让建模排期读取统一领域层。
5. 最后再接财务测算。

每一步都要保证页面仍能打开，并用回归样本检查。
